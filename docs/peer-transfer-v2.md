# Přímý protokol v2 – úplný přenos a Android discovery/UI

Transport je TLS 1.2/1.3 s oběma certifikáty a schválenými instalačními UUID/otisky. Párování viz etapa 8 v update-39-progress. Každý směr používá sekvenční dávku nejvýše 16 neměnných snapshotů; iniciátor nejprve odesílá, pak přijímá. Všechny JSON rámce mají čtyřbajtovou big-endian délku a striktní UTF-8, limit 20 MiB (řídicí hlavičky 4 KiB), hloubku 100. `working` rámce během lokálního hashování chrání před falešným timeoutem; žádné nejsou vložené do binárního těla. Nečinný socket včetně blokovaného writeru má watchdog 45 s.

Snapshot: `format:cz.zamerovac.sync.snapshot`, `version:2`, `sourceId`, `data` a `media:[{id,hash,size,mime,name}]`. Data mají schema 1; lokální `prefs` ani `created` se nepřenášejí. Vektory jsou `syncClock`, koš `syncTombstones` a legacy `trashPurgedIds`. Textové kóty zůstávají beze změny; nepřesně přenosná čísla nad 2^53−1 se odmítnou. Média zahrnují `media`/`audioMedia` i detail a historii `items` ve formě JSON řetězce. Manifest musí přesně pokrývat všechny reference. ID přílohy `[a-zA-Z0-9_-]{3,120}`, SHA-256 64 hex, délka 1 až 2 GiB.

Kanonické bajty: **RFC8785 JCS**, UTF-8, SHA-256. Android používá `java-json-canonicalization` 1.1 (Apache-2.0, licence v assets/licenses). Neplatné Unicode surrogate řetězce a duplicitní JSON klíče se odmítnou. Sdílená zlatá fixture `app/src/test/resources/sync-canonical-v2.json` ověřuje Java/ECMAScript bajty, exponenty, zápornou nulu, Unicode a ID práce. Budoucí Windows/iOS musí použít totožné pravidlo, nikoli běžný JSON encoder s jiným formátem čísel.

ID práce = SHA-256(JCS `{format:"cz.zamerovac.sync.job",version:2,peer,kind,hash,sourceRef,mediaId}`), nepřítomné reference jako JSON null. `sourceRef` identifikuje snapshot hash, nikoli cestu. Přílohy se streamují 64 KiB bloky, dočasně se ukládají do `.peer-v2-<uuid>.tmp`, kontroluje se velikost/hash a fsync. Originál se nikdy nepřepisuje: stejný ID/jiné bajty přenos výslovně zastaví. Zdroj i příjemce zachovají původní kopii. Přenos bajtů zatím obnovuje celý nedokončený soubor, potvrzené soubory přenášet znovu nemusí.

Sekvence: `batch(count)` → pro každou položku `snapshot(id,hash,size)` + surový rámec snapshotu → `need(hash,ids)` → pro každý ID `blob(id,jobId,hash,size)` + přesně size bajtů → `ack(id,hash,size,committed:true)` → `commit(id,hash)` → finální `ack`. Příjemce ověřuje zdroj snapshotu vůči TLS UUID. Finální ACK se odešle až po nové kontrole všech souborů a potvrzeném atomickém merge nejnovější lokální databáze. Souběžné neporovnatelné změny se označí a uchovají, nevolí se podle času telefonu. Souběžné čištění koše může přenos zastavit jako čekající, nikdy potvrdit neúplný projekt.

Fronta i připravené snapshoty jsou v Android no-backup úložišti (nekopírovat cizí identitu/frontu systémovou obnovou). Každá příloha má samostatný durable ACK; ztracený ACK se řeší opakováním a kontrolou existujícího originálu. Příprava novější revize smí zrušit starší pending snapshot jen s důkazem kauzálního zahrnutí všech záznamů a tombstones. Nikdy se při tom nemaže historická záloha. Zdrojová média nevlastní outbox: po výslovném vysypání koše mohou chybět a starý neodeslaný snapshot zůstane označený chybou.

**Testy a omezení:** `PeerTransferTest`, `SyncCanonicalTest` mají běžet v nativním CI. Skutečné JVM loopback TLS, dva oddělené datové adresáře/prefs, celý obousměrný přenos, přerušení 19/30, znovuotevření, místní editace při přenosu, kolize bajtů, částečné/poškozené soubory, podvržený source, nebezpečná metadata a konzervativní coalescing. Testy neověřují rádio, Android Keystore, uživatelské párovací obrazovky ani Drive. Android koordinátor musí zajistit nejvýše jednu relaci ke konkrétnímu peer přes všechny cesty, zavření socketu po revokaci a pravdivé čekání nových lokálních změn. Koordinátor/UI jsou zapojené od etapy 10; automatické obnovení známé P2P skupiny od etapy 20.

## Android integrace (etapa 10)

Nyní se aktivuje explicitně z obrazovky Synchronizace zařízení. LAN mDNS `_zamerovac._tcp.` → Wi-Fi-bound socket; obecný Wi-Fi P2P → owner IP, port 42391. Nové oprávnění NEARBY_WIFI_DEVICES od Android 13, předtím ACCESS_FINE_LOCATION; radio feature optional. Předání endpointu z JS je jen klíč nativně nalezené služby, nikdy uživatelem podstrčený host/URL. Instalační ID/certifikát se ověří až uvnitř TLS. Hello navíc obsahuje `paired`; pokud jedna strana nemá trvalou důvěru, obě znovu porovnávají kód v explicitním pairing okně. Současné opačné relace mají shodnou preferovanou orientaci podle UUID a sdílený peer zámek. Při odebrání důvěry se pending outbox pro tohoto peer zruší, historické zálohy zůstávají.

Toto je skutečný Android kód, **dosud bez fyzického ověření** rádia/Keystore. Automatiku od etapy 21 vlastní uživatelem zapnutá foreground služba connectedDevice s oznámením a vypnutím; obrazovka je jen dočasný observer. Od etapy 20 se při zániku skupiny nejvýše jednou za minutu hledá dříve ověřená rádiová adresa, následně je povinné očekávané instalační UUID a pin certifikátu ještě před přenosem dat. Rádiová adresa se uloží jen po úspěšném TLS spojení s vlastníkem skutečné P2P skupiny; sama nepovoluje párování. Je pouze v no-backup registru, ne v UI/cloud/záloze. Změněná či znepřístupněná rádiová adresa vyžaduje ruční výběr; služba může běžet i po zavření obrazovky, ale nepřetržitý provoz při Doze/omezeních výrobce není fyzicky potvrzen. Opožděné callbacky po rozpadu skupiny/kanálu nebo close se ignorují. Bez routeru není vyžadován internet/Google účet. Budoucí iOS/Windows potřebují vlastní discovery adaptér; P2P zde není slib kompatibility s rádiem iPhone.

## Životní cyklus služby (etapa 21)

DirectSyncService není exportovaná, deklaruje connectedDevice a příslušná oprávnění Androidu. Spouští se z viditelné aplikace při povolení/párování a při návratu se zapnutým místním přenosem. Generické oznámení neobsahuje zakázky/jména/MAC; obsahuje otevření aplikace a explicitní vypnutí. START_STICKY dovolí systému případné obnovení, není to garance restartu po force-stop/boot. Bez nastaveného directSyncEnabled se nepřipojí; odmítnutý start foreground ukáže problém, neznačí úspěch, nechá DB/frontu a službu ukončí.

PeerRuntime drží jediný application coordinator a připojované UI observery; Activity onStop/onDestroy jej nezavírá. Při ztrátě posledního viditelného observeru se ukončí párování. Potvrzená DB není závislá na doručení UI callbacku. Návrat načte aktuální potvrzený disk přes existující edit/CAS guard, nikdy nepřehraje starý screen snapshot. Při skutečné autentizované relaci se obnovuje nejvýše 90s PARTIAL_WAKE_LOCK; nečinnost/close jej pustí a pozdní callback jej neobnoví. Služba nesmí měnit systémová battery-exemption nastavení.

DirectSyncServiceTest ověřuje Android service/activity lifecycle, notification/STOP/denied/sticky, zachování DB/fronty, oddělení UI observerů, čerstvý resume callback a uvolnění locku. Koordinátor je v tomto lifecycle testu mock; skutečný datový/TLS přenos má samostatné integrační testy. Doze, výrobci, skutečný proces-kill/restart a OS rádiová omezení vyžadují fyzické ověření.

## Oznámení místní obnovy (etapa 28, volitelné v2 pole)

Autentizovaný `batch` může obsahovat `recovery`: prázdný řetězec před první obnovou nebo UUID v4 poslední místní DB recovery éry. Není to identita instalace, kauzální hodina ani hodnota projektu. Příjemce uloží změnu ke schválenému peeru a zruší jeho lastAck, takže znovu nabídne aktuální metadata; příjemce ověří existující média a požádá jen o chybějící. Recovery od initiatora se projeví před responder prepare. Pokud se obnovil responder a initiator již poslal prázdnou dávku, novou nabídku odešle v následující relaci. Opakování stejného UUID znovu ACK neruší. Neplatné typy/UUID se odmítnou, neznámý peer není povolen. Starší v2 peer pole ignoruje; pro automatické recovery je nutná aktualizace obou aplikací.

PeerOutbox před použitím generační cache ověří čitelnost DB, aby dříve zachycený snapshot nezakryl nový fallback. Lokální recovery journal se nepřenáší v projektu ani historické záloze. Skutečné TLS testy pokrývají obě role po dříve dokončeném přenosu, bez nové uživatelské editace. Rádio/OEM a náhodná poškození fyzického úložiště tím nejsou ověřená.

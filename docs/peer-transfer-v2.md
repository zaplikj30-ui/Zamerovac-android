# Přímý protokol v2 – implementované třídy, dosud bez Android discovery/UI

Transport je TLS 1.2/1.3 s oběma certifikáty a schválenými instalačními UUID/otisky. Párování viz etapa 8 v update-39-progress. Každý směr používá sekvenční dávku nejvýše 16 neměnných snapshotů; iniciátor nejprve odesílá, pak přijímá. Všechny JSON rámce mají čtyřbajtovou big-endian délku a striktní UTF-8, limit 20 MiB (řídicí hlavičky 4 KiB), hloubku 100. `working` rámce během lokálního hashování chrání před falešným timeoutem; žádné nejsou vložené do binárního těla. Nečinný socket včetně blokovaného writeru má watchdog 45 s.

Snapshot: `format:cz.zamerovac.sync.snapshot`, `version:2`, `sourceId`, `data` a `media:[{id,hash,size,mime,name}]`. Data mají schema 1; lokální `prefs` ani `created` se nepřenášejí. Vektory jsou `syncClock`, koš `syncTombstones` a legacy `trashPurgedIds`. Textové kóty zůstávají beze změny; nepřesně přenosná čísla nad 2^53−1 se odmítnou. Média zahrnují `media`/`audioMedia` i detail a historii `items` ve formě JSON řetězce. Manifest musí přesně pokrývat všechny reference. ID přílohy `[a-zA-Z0-9_-]{3,120}`, SHA-256 64 hex, délka 1 až 2 GiB.

Kanonické bajty: **RFC8785 JCS**, UTF-8, SHA-256. Android používá `java-json-canonicalization` 1.1 (Apache-2.0, licence v assets/licenses). Neplatné Unicode surrogate řetězce a duplicitní JSON klíče se odmítnou. Sdílená zlatá fixture `app/src/test/resources/sync-canonical-v2.json` ověřuje Java/ECMAScript bajty, exponenty, zápornou nulu, Unicode a ID práce. Budoucí Windows/iOS musí použít totožné pravidlo, nikoli běžný JSON encoder s jiným formátem čísel.

ID práce = SHA-256(JCS `{format:"cz.zamerovac.sync.job",version:2,peer,kind,hash,sourceRef,mediaId}`), nepřítomné reference jako JSON null. `sourceRef` identifikuje snapshot hash, nikoli cestu. Přílohy se streamují 64 KiB bloky, dočasně se ukládají do `.peer-v2-<uuid>.tmp`, kontroluje se velikost/hash a fsync. Originál se nikdy nepřepisuje: stejný ID/jiné bajty přenos výslovně zastaví. Zdroj i příjemce zachovají původní kopii. Přenos bajtů zatím obnovuje celý nedokončený soubor, potvrzené soubory přenášet znovu nemusí.

Sekvence: `batch(count)` → pro každou položku `snapshot(id,hash,size)` + surový rámec snapshotu → `need(hash,ids)` → pro každý ID `blob(id,jobId,hash,size)` + přesně size bajtů → `ack(id,hash,size,committed:true)` → `commit(id,hash)` → finální `ack`. Příjemce ověřuje zdroj snapshotu vůči TLS UUID. Finální ACK se odešle až po nové kontrole všech souborů a potvrzeném atomickém merge nejnovější lokální databáze. Souběžné neporovnatelné změny se označí a uchovají, nevolí se podle času telefonu. Souběžné čištění koše může přenos zastavit jako čekající, nikdy potvrdit neúplný projekt.

Fronta i připravené snapshoty jsou v Android no-backup úložišti (nekopírovat cizí identitu/frontu systémovou obnovou). Každá příloha má samostatný durable ACK; ztracený ACK se řeší opakováním a kontrolou existujícího originálu. Příprava novější revize smí zrušit starší pending snapshot jen s důkazem kauzálního zahrnutí všech záznamů a tombstones. Nikdy se při tom nemaže historická záloha. Zdrojová média nevlastní outbox: po výslovném vysypání koše mohou chybět a starý neodeslaný snapshot zůstane označený chybou.

**Testy a omezení:** `PeerTransferTest`, `SyncCanonicalTest` mají běžet v nativním CI. Skutečné JVM loopback TLS, dva oddělené datové adresáře/prefs, celý obousměrný přenos, přerušení 19/30, znovuotevření, místní editace při přenosu, kolize bajtů, částečné/poškozené soubory, podvržený source, nebezpečná metadata a konzervativní coalescing. Testy neověřují rádio, Android Keystore, uživatelské párovací obrazovky ani Drive. Android koordinátor musí zajistit nejvýše jednu relaci ke konkrétnímu peer přes všechny cesty, zavření socketu po revokaci a pravdivé čekání nových lokálních změn. Tyto navazující části ještě nejsou zapojené do UI.
